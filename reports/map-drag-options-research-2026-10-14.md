# 지도 드래그 개선안 비교·보완 조사

조사일: 2026-10-14. 대상: 현재 저장소의 Kakao Maps JS + Supercluster + CustomOverlay 구현. 앱 구현은 수정하지 않았다.

**권고:** 둘 중 하나만 먼저 한다면 1번(이동 중 갱신 중단). 최종적으로는 2번(화면 주변 결과 조회)을 함께 적용하고, 긴 이동에서만 제한적으로 핀을 보충하는 방식이 저사양 기기의 조작 반응과 핀 표시 연속성을 함께 다루기 좋다. 이는 아래 코드 검증과 공식 구현 사례를 바탕으로 한 설계 판단이며, 기기 성능 개선율이 실측된 결론은 아니다.

## 판단의 근거

이전 [코드 감사](map-drag-code-audit-2026-10-14.md)와 [실행 테스트](map-drag-code-audit.test.ts)에서 확인한 사실:

- 같은 데이터·줌의 드래그에서는 클러스터 재계산과 `getLeaves`를 하지 않는다. 캐시된 전체 그룹을 반복 순회한다.
- 합성 100군집 중 화면 주변 1개, 작은 이동 60회 조건에서 그룹 방문 6,000회, 클러스터 재계산·HTML 생성·오버레이 추가/제거는 각각 0회였다.
- 준비된 화면 범위가 달라지는 이동에서는 `idle` 전에도 오버레이 추가/제거가 실행됐다.
- 실제 DOM은 이미 화면+100px 주변만 생성한다. 2번은 **계산·조회 범위를 줄이는 개선**이다. 전국 DOM을 없애는 개선이라고 설명하면 부정확하다.
- 기존 코드에는 프레임별 4ms 협력적 작업 분할, 기존 오버레이 재사용, 화면 안 추가 우선 처리가 이미 있다. 이를 새로 도입한 효과로 계산하지 않는다.

이번 조사에서 실제 Android 프로파일이나 새 최적화 구현의 벤치마크는 실행하지 않았다. 기존 감사의 32개 테스트 결과는 현재 코드 동작에 관한 근거다.

## 1번·2번·결합안 비교

| 기준 | 1번: 이동 중 갱신 중단 | 2번: 화면 주변만 조회 | 결합: 주변 조회 + 이동 중 갱신 억제 |
|---|---|---|---|
| 줄이는 작업 | 드래그 중 앱 순회·HTML 준비·추가/제거 | 화면 밖 그룹 순회·새 줌의 불필요한 구성원 조회 | 작업 횟수와 매 작업의 처리 범위를 함께 축소 |
| 드래그 반응 | 움직이는 동안 앱의 해당 작업을 멈춘다는 효과가 명확 | 이동 중 작업은 남지만 대상이 줄어듦 | 일반 이동은 정지, 범위 이탈 때 작은 작업만 허용 가능 |
| 새 영역의 핀 표시 | 이동 종료까지 지연 가능 | 이동 중에도 현재 방식으로 갱신 가능 | 기본은 종료 후, 긴 이동에서는 제한적으로 보충 |
| 이동 종료 후 | 전체 결과 순회가 여전히 필요 | 주변 결과만 처리 | 주변 결과만 처리하므로 1번의 종료 후 지연을 줄이는 방향 |
| 전국을 한 화면에 볼 때 | 이동 중 작업 억제는 유효 | 대부분 화면 안이므로 범위 축소 이득이 작음 | 주로 1번의 이득 |
| 좁은 지역을 확대해서 볼 때 | 이동 중 작업 억제 | 전국 대비 처리 범위가 작아지기 좋음 | 두 기법이 서로 보완 |
| 메모리 | 중단 자체로 큰 변화 없음. 여백 확대 시 DOM 증가 | 제한된 캐시 설계 시 줌별 전체 구성원 보관을 줄일 여지. 원본 데이터·전국 인덱스는 유지 | 데이터 캐시·DOM 범위를 별도로 제한해야 함 |
| 구현 범위 | 주로 훅의 이벤트·작업 예약. 중간 이하 | 조회 API, 그룹 ID, 캐시, 확대 단계 분기. 중간 이상 | 상대적으로 큼. 변경을 나눠 검증 가능 |
| 회귀 위험 | 작업 재개 누락, 데이터·줌 변경과 경합, 긴 드래그의 핀 공백 | 화면 경계 핀 누락, 오래된 캐시, HTML 재생성, 클릭 데이터 불일치 | 두 범주의 검증 필요 |
| 남는 비용 | 이미 붙은 오버레이를 SDK가 이동·그리는 비용 | 같은 화면의 오버레이 수·복잡도, 전국 인덱스 생성 | 동일. 두 안으로 모든 렌더링 병목이 없어지지는 않음 |

카카오 데브톡 답변은 마커 DOM이 많으면 이동 중 위치 보정 비용이 커지고, 화면 범위·클러스터링·표시 밀도 조절을 고려하라고 설명한다. 따라서 이 두 안이 화면에 남아 있는 오버레이 자체의 비용까지 없애 준다고 예상하면 안 된다. [카카오 데브톡 원문](https://devtalk.kakao.com/t/topic/132162)

## 1번의 단점과 줄이는 방법

### A. 긴 드래그에서 새 지역 핀이 늦게 보임

**원인:** 현재는 화면 밖 100px까지만 미리 표시한다. 그보다 멀리 이동하고 추가를 전부 멈추면 아직 만들지 않은 핀이 새 화면에 들어온다.

**보완 제안:**

1. 이미 표시한 핀은 그대로 유지한다. 드래그 시작 때 전부 지우거나 숨기지 않는다.
2. 현재 준비된 범위 안에서는 무거운 작업을 하지 않는다. 범위 이탈 여부를 확인하는 작은 작업만 남긴다.
3. 범위를 벗어나는 긴 이동에서는 **2번의 주변 조회 결과로만** 새 영역을 제한적으로 보충한다. 갱신은 일정 간격보다 자주 하지 않고, 작업은 프레임별로 나눈다. 너무 멀어진 오버레이도 같은 작업 예산에서 정리해 연속 이동 시 누적되지 않게 한다.
4. 이동이 정착하면 제한 없이 한 번에 몰아서 처리하지 않고 기존 작업 분할로 최종 상태를 완성한다.

Leaflet의 GridLayer는 모바일에서 이동 종료 후 타일 갱신을 기본으로 하고, 이동 중 갱신 간격과 주변 타일 유지 옵션을 제공한다. **타일에 관한 사례이며 우리 핀에 대한 성능 검증은 아니다.** 조작 반응과 새 영역 표시 사이의 절충을 공식 구현이 어떻게 다루는지 참고했다. [Leaflet GridLayer 문서](https://leafletjs.com/reference.html#gridlayer-updatewhenidle)

갱신 제한 150~200ms, 이동 중 한 작업 묶음의 협력적 예산 1~2ms는 구현 시 비교할 **초기 실험 후보**일 뿐이다. 최적값이나 성능 보장이 아니다. 빠르게 멀리 이동하면 제한적 보충으로도 지연은 남을 수 있다. 보충을 허용한 절충안은 엄격한 1번과 달리 이동 중 작업이 0회가 되지 않는다.

### B. 미리 표시할 여백을 키우면 다시 무거워짐

390×844 화면에서 사방 여백을 100px → 200px로 키우면 포함 면적은 615,960 → 982,760px², 약 **59.5% 증가**한다. 균일한 표시 밀도를 가정할 때 준비 대상도 그 비율로 늘 수 있다는 기하학적 설명이다. 실제 핀 수·메모리·처리 시간이 59.5% 늘어난다는 측정 결과는 아니다.

**보완 제안:** 화면 주변의 좌표·클러스터 결과 캐시는 조금 넓게 준비해도, 지도에 실제 붙이는 오버레이는 작은 여백만 유지한다. 지도에서 뗀 오버레이를 재사용하려면 별도의 제한된 보관함을 둔다. 캐시 준비만으로 핀이 보이는 것은 아니므로, 긴 이동의 표시 공백은 위의 제한적 보충과 함께 다룬다.

표시 중인 마커와 재사용 캐시를 분리하는 패턴은 Mapbox의 HTML 클러스터 예제에서도 확인된다. 예제는 `cluster_id`로 마커를 재사용하고 화면에서 사라진 마커를 분리한다. 해당 예제의 매 프레임 갱신 정책이나 무제한 캐시를 그대로 도입하자는 제안은 아니다. 우리 앱은 필터·데이터 세대와 캐시 상한을 추가해야 한다. [Mapbox HTML 클러스터 예제](https://docs.mapbox.com/mapbox-gl-js/example/cluster-html/)

### C. 손을 놓을 때 작업이 몰리거나, 갱신이 다시 시작되지 않음

**보완 제안:**

- `idle`을 최종 갱신 기준으로 사용한다. 지도 타일 다운로드를 기다리는 `tilesloaded`에 의존하지 않는다.
- `idle` 직후 별도 긴 debounce를 더하지 않고 다음 처리 기회에 시작한다. 화면 안 우선 처리와 프레임 분할은 이미 있으므로 보존한다.
- 드래그·줌·필터/데이터 변경에서 모든 예약이 같은 이동 상태를 검사하도록 한다. 낡은 줌·데이터의 작업은 폐기하고 최신 조건을 최종 처리한다.
- 핀을 아직 처음 그리는 중에 사용자가 이동한 경우, 연속 드래그, 관성 이동, 현재 위치/지역 이동, 언마운트/재진입을 검증한다.

카카오 문서상 `idle`은 중심·확대 수준 변경에 발생하되 애니메이션 도중에는 발생하지 않는다. `tilesloaded`는 타일을 새로 받지 않는 미세 이동에서는 발생하지 않는다. 따라서 최종 핀 갱신을 후자에만 걸면 누락될 수 있다. [Kakao Map 이벤트](https://apis.map.kakao.com/web/documentation/#Map_idle)

## 2번의 단점과 줄이는 방법

### A. 단순 bbox 변경은 캐시와 확대 표시를 깨뜨릴 수 있음

**보완 제안:**

- 전국 데이터를 바탕으로 만든 동일 인덱스에 화면+여백 bbox를 질의한다. 화면 안 원본 데이터만 먼저 잘라 새로 클러스터링하지 않는다. 그래야 같은 줌에서 이동할 때 묶음이 흔들리는 것을 피할 수 있다.
- 현재 `level`만으로 된 결과 캐시는 데이터 세대·줌·조회 범위를 함께 관리하도록 변경한다. 같은 줌에서 이전 조회 범위가 새 화면을 충분히 포함하면 범위 조회도 재사용할 수 있다.
- level 4 이상은 군집 중심 범위 조회, level 1~3은 현재처럼 개별 핀을 표시할 수 있도록 원본 포인트 범위 조회를 사용한다. 군집 중심이 영역 밖이어도 내부 구성원이 영역 안에 있을 수 있으므로 분리해야 한다.
- 화면 가장자리에 몸통이 걸치는 핀을 고려한 여백을 유지한다. 새 핀 추가 범위와 기존 핀 제거 범위를 조금 다르게 하면 경계 왕복 때 붙였다 떼는 횟수를 줄일 수 있다. 제거 범위 확장에는 DOM 증가 비용이 있으므로 작게 제한한다.

Supercluster는 인덱스 생성 후 bbox와 줌으로 결과를 조회하는 API를 제공한다. 기존 감사에서 실제 설치 버전으로 군집의 좌표·ID·구성원 유지와 확대 상태의 경계 예외를 확인했다. [Supercluster API](https://github.com/mapbox/supercluster#getclustersbbox-zoom), [로컬 검증](map-drag-code-audit.test.ts)

### B. 범위 조회마다 객체를 새로 만들면 HTML 캐시가 무효화됨

**보완 제안:** 그룹 객체/렌더 결과를 `데이터 세대 + 줌 + cluster_id`로 재사용한다. 개별 핀은 해당 데이터 세대 안에서 안정적인 입력 인덱스 또는 확실한 고유 ID를 사용한다. `spotId`가 없는 명소도 있으므로 그것만 키로 쓰지 않는다. 데이터 세대가 바뀌면 이전 군집 ID를 그대로 믿지 않는다. 클릭 핸들러도 최신 구성원을 참조하게 유지한다.

동일 그룹의 HTML·오버레이를 재사용하는 것은 현재 최적화의 장점이므로, bbox 전환 때문에 이를 잃으면 개선 폭이 줄거나 상황에 따라 악화될 수 있다.

### C. 캐시가 쌓이거나 전국 화면에서 이득이 작음

**보완 제안:** 마지막 조회 범위를 중심으로 결과를 보관하고, 화면 밖 재사용 캐시는 최근 사용 순서와 개수/메모리 예산으로 제한한다. 보이는 핀을 상한 때문에 임의로 숨기지 않는다. 전국 화면에서는 주변 범위가 전체 결과와 비슷하므로 결과 캐시를 재사용하고 반복 질의를 피한다.

이 경우에도 1번으로 이동 중 반복 작업 횟수를 줄일 수 있다. 2번 단독은 화면 밖 데이터가 적을수록 이점이 작고, 범위 질의·객체 생성 비용이 추가되면 기존 캐시 순회보다 불리할 수도 있다.

### D. 구성원 조회를 클릭까지 미루면 기존 꽃 표시·클릭 기능 변경 범위가 커짐

우리 클러스터는 단순 개수뿐 아니라 상태 비율, 꽃 정보가 있는 명소 중 대표 상태, 해당 상태의 대표 꽃을 계산한다. 클릭 시 구성원 bounds와 목록도 사용한다.

**1차 구현에서는 화면 주변 군집의 구성원을 그대로 조회하고 캐시하는 편을 권한다.** 이것만으로도 화면 밖 군집의 `getLeaves`는 제외된다. 이후 이 비용이 문제일 때 상태별 집계를 인덱스에 저장하고 구성원 조회를 지연하는 추가 변경을 검토한다. 단순 개수 집계만 도입하면 현재 색·꽃 선정과 동률 처리까지 보존하지 못한다.

Supercluster는 속성 집계를 위한 map/reduce를 지원한다. 이 기능의 존재는 확인됐지만 우리 표시 규칙을 그대로 집계로 옮기는 작업은 별도 구현·검증이 필요하다. [Supercluster 속성 집계](https://github.com/mapbox/supercluster#property-mapreduce-options)

## 효과를 수치로 해석할 때

아래는 기존 합성 테스트 조건에서 **처리 그룹 수만** 비교한 설명용 계산이다. 개선 코드를 실행한 벤치마크가 아니다. 60번 이동 모두 같은 표시 범위이고 각 작업이 끝날 여유가 있으며, 종료 후 최종 갱신을 한 번 한다고 가정한다.

| 방식 | 이동 중 그룹 방문 | 종료 후 그룹 방문 | 해석 |
|---|---:|---:|---|
| 현재 방식 | 6,000 | 100 | 전체 100그룹을 반복 확인 |
| 엄격한 1번 | 0 | 100 | 반복 횟수 제거, 마지막 전체 순회는 남음 |
| 2번만, 매 이동 주변 1그룹 처리 | 약 60 | 약 1 | 조회·객체 관리 비용은 별도. 범위 캐시 재사용 시 더 적어질 수 있음 |
| 엄격한 1번+2번 | 0 | 약 1 | 횟수와 범위 동시 축소 |

권장하는 긴 이동 보충형 결합안은 범위 이탈 때 작업하므로 0회 보장을 하지 않는다. 또한 HTML/DOM·지도 SDK·브라우저 그리기 비용이 섞여 있어 이 숫자를 FPS 배수나 성능 개선율로 환산할 수 없다.

## 최종 선택과 적용 순서

**하나만 고른다면 1번:** 현재 사용자 불편인 이동 중 끊김을 직접 겨냥하고, 변경 범위가 상대적으로 작다. 긴 이동에서 새 핀이 늦게 나타나는 것이 허용돼야 한다.

**이동 중 핀 표시 연속성이 최우선이면 2번:** 핀을 계속 갱신하는 동작을 유지하면서 계산 범위를 줄인다. 다만 생성·제거와 지도 렌더링 경합은 남으므로 저사양 기기의 드래그를 충분히 개선한다고 보장할 수 없다.

**제품에 최종 적용할 방향은 결합안:** 기본은 이동 중 무거운 작업을 억제하고, 준비한 범위를 벗어날 때만 주변 핀을 제한적으로 보충하며, `idle`에서 완성한다. 두 안의 장점을 함께 사용하되 긴 드래그의 일시적인 지연을 완전히 없앤다는 목표는 두지 않는다.

구현·검증은 다음 순서가 명확하다.

1. 1번을 독립적으로 적용해 현재와 같은 데이터·줌·이동 경로에서 비교한다. 효과가 없으면 기존 오버레이/SDK 렌더링 비중을 먼저 확인한다.
2. 2번을 별도로 적용해 이동 종료 후 첫 핀/전체 핀 표시 시간과 경계·확대 정확성을 비교한다.
3. 1번의 긴 이동 공백을 확인하고 제한적 보충을 결합한다. 엄격 중단과 절충안의 프레임 지연·핀 공백 시간을 함께 비교한다.

이 순서는 구현 효과를 구분하기 위한 제안이다. 최종 제품 구조는 세 단계 결과에 따라 조정한다. Android 앱이라는 이유만으로 저사양이라고 가정하거나 모든 기기에 같은 공격적인 중단 정책을 고정할 필요는 없다.

## 확인 기준

- 같은 기기·앱 빌드·데이터·줌에서 작은 왕복 드래그, 화면 두 개 이상 이동, 빠른 연속 플릭, 줌 직후 이동, 이동 중 데이터 변경을 비교.
- 드래그 프레임 간격의 상위 구간과 긴 JS 작업, 표시 오버레이 수를 확인.
- `idle` → 첫 새 핀 표시 / 해당 화면 갱신 완료 시간, 이동 중 새 영역이 핀 없이 보인 시간을 함께 확인.
- 동일 좌표·줌의 최종 핀 집합, 군집 개수·상태 링·대표 꽃, 클릭 확대·목록 결과가 기존과 같은지 확인.
- 장시간 왕복 시 캐시와 오버레이가 계속 늘어나지 않는지 확인.

## 조사 출처의 적용 범위

- [Kakao Map 문서](https://apis.map.kakao.com/web/documentation/#Map_idle): 갱신 이벤트 선택의 직접 근거.
- [카카오 데브톡](https://devtalk.kakao.com/t/topic/132162): DOM 수와 지도 이동 비용에 대한 제공자 측 설명. 우리 앱의 병목을 실측한 자료는 아님.
- [Supercluster](https://github.com/mapbox/supercluster): 범위 조회·구성원 조회·속성 집계의 직접 근거. 로컬 설치 코드와 테스트를 우선해 검토.
- [Leaflet GridLayer](https://leafletjs.com/reference.html#gridlayer-updatewhenidle): 모바일 이동 종료 갱신, 간격 제한, 주변 유지의 공식 사례. 타일 정책을 우리 핀에 적용하는 부분은 설계 제안.
- [Mapbox HTML 클러스터](https://docs.mapbox.com/mapbox-gl-js/example/cluster-html/): ID 기반 HTML 마커 재사용과 화면 부착 상태 분리의 공식 사례. Mapbox의 엔진 성능을 카카오로 환산하지 않음.
- [Leaflet.markercluster](https://github.com/Leaflet/Leaflet.markercluster#defaults): 먼 화면 밖 항목 제거와 작업 분할을 지원하는 공식 구현 사례. 우리 코드는 이미 해당 원칙의 일부를 구현함.

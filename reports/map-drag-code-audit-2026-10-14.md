# 지도 드래그 코드 검증 — 2026-10-14

> 변경 전 감사 기록이다. 이후 사용자 요청으로 최적화를 구현했으며, 같은 테스트 파일은 개선 후 회귀 검증으로 갱신했다. 구현 결과는 [후속 기록](map-drag-implementation-2026-10-14.md)을 참고한다.

## 결론과 앞선 설명의 정정

1. **드래그 중 애플리케이션의 오버레이 갱신 작업이 실행된다:** 실제 훅을 실행해 확인했다. 다만 기존 오버레이를 매번 다시 만드는 것은 아니다. 이동해도 표시 대상이 같으면 HTML 생성과 SDK `setMap` 호출은 모두 0회다.
2. **화면 밖 클러스터도 처리한다:** 전체 결과를 최초 조회·구성원 펼치기 하고, 같은 줌에서 이동할 때는 그 캐시 배열을 순회한다. **매 드래그 프레임마다 클러스터를 재계산하거나 `getLeaves`를 호출한다는 해석은 틀리다.**
3. 두 작업이 존재한다는 사실과 실제 저사양 기기의 주된 병목이라는 판단은 다르다. 이번 검증은 호출 경로·횟수를 입증하며, 실제 Android WebView의 FPS·SDK 내부 레이아웃·페인트 비용은 측정하지 않았다. 앞선 답변의 개선 우선순위는 병목이 실측된 결론으로 받아들이면 안 된다.

앱 구현은 변경하지 않았다. 재현 가능한 검증 파일 `map-drag-code-audit.test.ts`를 이 보고서와 함께 추가했다.

## 검증 방법

- 실제 `useMapCluster`, `clusterSpots`, HTML 생성 함수, `advanceFrame` 및 설치된 Supercluster 코드를 실행했다.
- 함수 스파이는 원래 구현을 호출한다. 반환 클러스터 배열에 Proxy를 씌워 실제 훅의 반복문에서 소비하는 그룹 수만 센다. 클러스터·스팟 객체와 캐시 참조는 유지한다.
- 카카오 SDK, 지도 좌표 투영, rAF, 시간은 대체했다. SDK `setMap` 호출 수는 셀 수 있지만 그 내부 비용은 측정하지 않는다.
- 합성 입력 200개 핀을 100개 군집으로 배치했다. 테스트 지도는 화면+100px 여백 안에 군집 하나가 들어오게 했다. 실제 운영 데이터·기기·지도 축척의 재현은 아니다.
- `performance.now()`의 가상 시간은 프레임 분할을 결정적으로 재현하기 위한 것이다. 아래 숫자는 소요 시간이나 FPS가 아니다. 60회의 테스트 rAF 실행을 1초 또는 60fps로 해석하면 안 된다.

## 1. 드래그 실행 경로

근거: [useMapPins.ts](../src/hooks/useMapPins.ts:242).

```text
dragstart
  isDragging = true, lastCenter = null, rAF 시작
    tick: getCenter로 중심 변경 확인
      변경됐으면 needsRefresh = true
      진행 중 job이 없을 때만 render generator 생성
      advanceFrame(job, 4)로 진행 중 job 이어서 처리
      dragging / refresh / job 중 하나라도 남으면 다음 rAF 예약

dragend
  isDragging = false만 변경 — 진행 중 job을 취소하지 않음

idle
  schedule() — 기존 job을 취소하고 새 화면을 다시 처리
```

- 중심이 계속 변하고 한 프레임 안에 job이 끝나면 매 프레임 전체 캐시를 순회한다.
- job이 길면 다음 프레임에서 이어서 처리한다. 매 프레임 처음부터 다시 시작하지 않는다.
- job은 시작할 때의 화면 범위를 갖는다. 도중에 이동해도 기존 범위의 작업을 마친 뒤 최신 화면을 처리한다. 해당 순서도 테스트로 확인했다.
- 중심이 멈췄고 job이 없으면 순회는 멈춘다. `isDragging`이 true인 동안 중심 확인 rAF는 계속 돈다.
- 핀 데이터가 드래그 도중 바뀌어도 effect의 `schedule()`이 작업을 시작한다. 드래그 이벤트 하나만 수정해서 모든 작업을 정지시킬 수 있는 구조는 아니다.
- `idle`은 최종 이동 프레임에서 이미 작업을 끝냈더라도 새 순회를 예약한다.

### 실제 호출 횟수

각 행은 초기 마운트를 마친 뒤 계측값을 초기화한 독립 시나리오다. 첫 행만 초기 마운트 자체다.

| 시나리오 | 인덱스 생성 | getClusters | getLeaves | 그룹 방문 | HTML 생성 | setMap 추가 / 제거 |
|---|---:|---:|---:|---:|---:|---:|
| 첫 표시: 100군집 중 1개만 화면 주변 | 1 | 1 | 100 | 100 | 1 | 1 / 0 |
| 같은 줌, 작은 이동 60회, 보이는 대상 동일 | 0 | 0 | 0 | 6,000 | 0 | 0 / 0 |
| dragstart 후 중심 이동 없이 60회 프레임 실행 | 0 | 0 | 0 | 100 | 0 | 0 / 0 |
| 같은 줌, 옆 군집으로 이동, dragend·idle 미발행 | 0 | 0 | 0 | 100 | 1 | 1 / 1 |
| 작업을 여러 프레임으로 분할한 상태에서 화면 변경, 두 작업 완료 | 0 | 0 | 0 | 200 | 1 | 1 / 1 |

따라서 **드래그 중 반복 순회**와 **표시 범위 변경 시 추가·제거**는 확인됐다. **같은 핀을 드래그할 때마다 재생성한다**는 설명은 맞지 않는다.

### 4ms의 의미

근거: [frameTask.ts](../src/lib/utils/frameTask.ts:2), [useMapPins.ts](../src/hooks/useMapPins.ts:84).

`advanceFrame`은 `task.next()`가 돌아온 뒤 시간을 검사한다. 개별 동기 작업을 중간에 중단하지 못한다. 캐시가 없는 경우의 `clusterSpots(...)` 전체 호출과 SDK 호출 하나는 `yield` 사이에 있는 단일 작업이다. 또한 애플리케이션의 작업 예산이 4ms라는 사실은 지도 SDK와 브라우저까지 포함한 전체 프레임 비용이 4ms라는 뜻이 아니다. 이번 테스트에서는 실제 시간 초과 여부를 측정하지 않았다.

## 2. 전체 결과 조회와 화면 밖 처리

근거: [mapCluster.ts](../src/lib/utils/mapCluster.ts:114), [useMapPins.ts](../src/hooks/useMapPins.ts:70).

캐시는 세 겹이다.

| 캐시 | 키 | 절약되는 작업 |
|---|---|---|
| indexCache | spots 배열 참조 | Supercluster 인덱스 생성 |
| clusterCacheRef | 지도 level | 전역 getClusters + 그룹별 getLeaves + 구성원 배열 생성 |
| viewCacheRef | ClusterGroup / MapSpot 객체 | 핀·클러스터 HTML과 라벨 생성 |

실행 테스트에서 다음을 확인했다.

- 같은 데이터·같은 줌의 드래그: 위 계산 캐시가 유지된다.
- 처음 방문하는 줌: 인덱스 생성 0회, 전역 결과 조회 1회, 테스트의 100군집에 대한 구성원 조회 100회.
- 이전 줌으로 복귀: 전역 결과와 구성원 조회 모두 0회.
- 같은 spots 배열로 부모 재렌더: 훅 작업 예약 없음.
- 내용이 같아도 새 spots 배열로 교체: 인덱스 재생성 및 전역 조회 실행.

### 반복 순회에서 수행하는 일

[useMapPins.ts:196](../src/hooks/useMapPins.ts:196)의 루프는 캐시된 모든 그룹을 돈다.

- level 4 이상: 복수 구성원 그룹은 중심 좌표로 화면+100px 범위를 판정한다. 단일 그룹은 개별 핀 좌표로 판정한다.
- level 1~3: 복수 그룹이어도 구성원을 전부 펼쳐 개별 핀 좌표로 판정한다.
- 화면 밖이면 HTML과 DOM을 만들기 전에 건너뛴다.
- 화면 안이면 HTML 캐시와 기존 entries를 확인한다. 기존 항목은 데이터 참조만 갱신한다.
- 그 뒤 기존 entries를 순회해 이번 화면에서 필요 없는 것만 제거한다. 추가할 항목만 새로 생성한다.

**전국 핀을 모두 DOM으로 올리는 구조는 아니다.** 첫 표시 테스트에서도 100군집의 구성원을 조회했지만 오버레이는 1개만 만들었다.

### 화면 bbox 조회 제안의 타당성과 조건

설치된 [Supercluster 소스](../node_modules/supercluster/index.js:146)의 `getClusters`는 이미 만들어진 줌별 트리를 범위 조회한다. 입력 데이터를 화면 크기로 잘라 새 인덱스를 만드는 동작이 아니다.

실제 라이브러리 테스트에서 동일 인덱스의 전체 조회 100군집 → 작은 bbox 조회 1군집으로 줄었고, 반환 군집의 ID·좌표·구성원은 유지됐다. bbox 밖의 구성원도 해당 군집에 그대로 남았다.

그러나 우리 훅에는 다음 조건이 있어 **bbox 인자만 바꾸면 완성되는 변경은 아니다.**

1. 현재 `clusterCacheRef`는 level만 키로 삼는다. 범위 조회 결과를 여기에 그대로 넣으면 같은 줌에서 다른 지역으로 이동해도 이전 영역 결과가 남는다. 조회 범위·캐시 무효화 설계를 함께 바꿔야 한다.
2. level 1~3은 군집 중심이 아니라 개별 구성원을 표시한다. 테스트에서 bbox 안에 개별 핀 1개가 있어도 군집 중심이 밖이면 군집 bbox 조회 결과는 0개가 됐다. 확대 상태에는 원본 포인트 범위 조회 등 별도 처리가 필요하다. 이는 같은 bbox에서의 결과 동등성 검증이며 실제 100px 여백을 둔 화면에서 핀 누락이 발생했다는 실측은 아니다.
3. 매 조회마다 새로운 그룹 객체를 만들면 현재 객체 기반 HTML WeakMap 캐시가 적중하지 않는다. 안정적인 군집 ID로 객체·렌더 결과를 유지하는 처리도 필요하다.
4. 전체 인덱스 생성은 그대로 필요하다. bbox 조회가 모든 초기 계산 비용을 제거하지는 않는다.

## 상위 컴포넌트 및 주석 확인

- [MapContainer.tsx:153](../src/components/Map/MapContainer.tsx:153)의 API 조건은 `KOREA_BBOX + applied.region`이다. 지도 중심·viewport가 query key 입력에 들어가지 않는다. 일반 드래그가 곧 API 재요청으로 연결되는 경로는 없다. 별도 쿼리 무효화·재조회는 다른 경로다.
- `allSpots`와 `spots`는 useMemo로 유지된다. viewport는 idle에서 갱신하지만 spots의 의존성이 아니므로 그 이유로 클러스터 캐시를 비우지 않는다.
- `useMapPins.ts:94`의 “조회 bbox는 격자 스냅” 주석은 현재 실행 코드와 맞지 않는다. 실제 쿼리는 고정 KOREA_BBOX이며 클러스터 조회는 전역 bbox다. 해당 주석을 근거로 동작을 판단하지 않았다.

## 개선 판단을 어디까지 내릴 수 있는가

- 1번 변경은 드래그 중 애플리케이션 순회와 추가·제거를 줄이는 데 직접 대응한다. 다만 화면 밖에 새로 나타나는 핀은 이동 종료까지 늦어질 수 있다. 기존 100px 여백을 넘는 긴 드래그에서 이 동작을 검증해야 한다. 진행 중 작업·데이터 변경·줌·관성 이동의 재개 시점도 함께 다뤄야 한다.
- 2번 변경은 화면 밖 결과의 반복 순회와 새 줌의 구성원 조회 범위를 줄이는 데 대응한다. 현재도 화면 주변 DOM만 올리므로, bbox 변경만으로 같은 화면의 오버레이 개수가 자동으로 줄지는 않는다.
- 두 변경 모두 기존에 화면에 떠 있는 오버레이를 지도 SDK가 이동·표시하는 비용을 없애지는 않는다. 따라서 실제 주된 병목이라고 단정하거나 개선율을 제시할 근거는 아직 없다.
- 원인 확정에는 실제 앱에서 같은 데이터·줌·드래그 경로로 애플리케이션 갱신을 잠시 중단한 비교 프로파일이 필요하다. 그때도 버벅임이 유지되는지, JS 작업·SDK 레이아웃·페인트 중 시간이 어디에 쓰이는지 확인해야 한다.

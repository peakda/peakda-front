# 지도 드래그 최적화 구현 결과

2026-10-14. [조사·선택안](map-drag-options-research-2026-10-14.md)에 대한 사용자 구현 요청을 반영했다.

## 적용 내용

- [useMapPins.ts](../src/hooks/useMapPins.ts): 기존 매 프레임 중심 확인/전체 그룹 순회 대신 `bounds_changed`마다 준비 영역의 유효성만 확인한다(O(1)). 완료된 100px 여백이 화면 + 80px(`REFILL_MARGIN_PX`)를 덮으면 갱신 작업을 예약하지 않는다. 즉 20px 움직일 때마다 화면 주변만 한 번 다시 그린다.
- 영역을 벗어나면 바로 주변 핀을 보충한다. 프레임 예산은 모든 경우 기존 4ms다. 진행 중 보충은 이동 이벤트마다 재시작하지 않고, 끝나는 즉시 범위를 다시 확인해 지속적인 이동에서도 굶지 않는다.
- `idle`에서 최종 영역을 갱신한다. 직전 보충으로 같은 영역을 이미 완성했다면 중복 작업을 생략한다. 드래그·관성·프로그램에 의한 이동 모두 `bounds_changed`로 처리하므로 `dragstart`/`dragend`는 듣지 않는다.
- 줌 시작/변경, 데이터 교체, 언마운트 때 낡은 작업과 타이머를 정리한다. 연속 줌 시작 시 이전 debounce도 취소한다.
- [mapCluster.ts](../src/lib/utils/mapCluster.ts): 전국 인덱스를 유지한 채 화면 주변 결과만 질의한다. 마지막 좌표 결과는 200px 여백까지 보관하지만, 구성원 조회·HTML·실제 오버레이는 기존 100px 여백 범위에 한정한다.
- 그룹을 데이터별 조회기 내부의 `cluster_id` / 원본 포인트 인덱스로 재사용해 기존 HTML WeakMap 캐시를 유지한다. 재사용 그룹 캐시는 256그룹·구성원 참조 합계 10,000개까지 보관한다. 이 상한은 화면 밖 재사용 캐시에 대한 것이며 화면에 보이는 핀을 상한 때문에 누락시키지 않는다.
- level 1~3은 원본 포인트 트리에서 조회해 군집 중심이 밖에 있는 개별 핀이 누락되지 않게 했다. level 4 이상은 기존 군집·개별 핀 표시 규칙을 유지한다.
- 원래 `clusterSpots`는 클릭 시 확대 가능 여부 판단 등에 그대로 사용한다. 클러스터 상태 링·대표 꽃 HTML과 API 조회 조건은 변경하지 않았다.

## 검증된 작업량 변화

이전 감사와 동일한 합성 입력 200핀/100군집, 가상 투영에서 화면 주변 1군집 조건이다. 시계와 SDK는 대체하고 실제 훅·Supercluster·HTML 코드를 실행했다. 아래는 FPS나 실행 시간 측정이 아니다.

| 항목 | 변경 전 | 변경 후 |
|---|---:|---:|
| 첫 표시의 군집 구성원 조회 | 100회 | 1회 |
| 첫 표시의 그룹 방문 | 100회 | 1회 |
| 같은 표시 영역 내 미세 이동 60회의 그룹 방문 | 6,000회 | 0회 |
| 위 이동 중 HTML 생성 / 오버레이 추가·제거 | 0회 | 0회 유지 |
| 위 이동 후 idle의 그룹 방문 | 100회 | 1회 |

60회 미세 이동은 각 경도 0.000001 증가, 가상 투영 10,000px/도 조건이다. 이동 종료 때까지 준비 영역을 벗어나지 않는 경우의 검증이며, 모든 드래그에서 그룹 방문 0회를 보장하는 수치는 아니다.

추가 확인:

- 준비 영역을 벗어난 첫 이동 이벤트에서 바로 보충을 예약하고, 진행 중 이벤트 29회는 합친다. 주변 군집 하나를 추가하고 이전 하나를 제거한다.
- 10px씩 드래그할 때 다음 군집은 핀 몸통이 화면에 걸치기 전에 이미 붙어 있다.
- 실제 SDK 순서(놓을 때 `idle` → `dragend`)로 드래그를 끝낸 직후 필터를 바꾸면 타이머 없이 바로 다시 그린다.
- 완료된 보충 영역과 같은 위치의 idle은 다시 순회하지 않는다.
- 움직임이 없는 드래그는 지속적인 rAF/타이머 루프를 남기지 않는다.
- 전체 level 1~13과 여러 bbox에서 이전 표시 규칙과 최종 그룹·구성원·좌표가 일치한다.
- 군집 중심 밖의 구성원, 확대 단계 개별 핀, 데이터 교체, HTML 재사용, 캐시 상한, 키보드/클릭 활성화, bounds 확대와 fallback 확대를 검증했다.
- 초기 작업 중 드래그, 연속 줌, 진행 중 보충의 지속 이동, 빈 필터 결과, 언마운트 정리를 검증했다.

## 보완: 첫 구현(PR #177)의 회귀 두 가지

첫 구현은 이동 중 범위 확인을 최대 160ms 간격으로 하고, `idle`에서 드래그 중이면 갱신을 건너뛰었다. 검증해 보니 두 회귀가 있어 위 내용으로 고쳤다.

1. **드래그 중 가장자리 핀이 늦게 뜸.** 준비 여유(100px − 핀 몸통 64px = 36px)를 넘은 뒤에도 최대 160ms 동안 확인하지 않아, 화면에 걸친 핀이 비어 보였다.
2. **드래그 직후 필터 반응이 약 160ms 늦음.** 실제 카카오 SDK는 드래그를 놓을 때 `idle`을 `dragend`보다 먼저 보낸다(헤드리스 Chromium, 마우스·Android UA 터치 모두, 누른 채 멈춰 있는 동안에는 `idle` 없음). 그래서 `idle`의 정착 갱신이 늘 건너뛰어지고 '이동 중' 상태가 남아, 다음 데이터 변경이 160ms 타이머·2ms 예산으로 처리됐다.

드래그 시뮬레이션(실제 훅·클러스터·HTML, 가짜 SDK·시계, 665핀, 순회 한 단계 2µs·오버레이 부착 0.5ms 가정, 1.5초 드래그)으로 비교했다. 시간 값은 이 비용 모델 위의 수치이고 실기기 측정이 아니다.

| | 변경 전(매 프레임 순회) | 첫 구현 | 보완 |
|---|---:|---:|---:|
| 늦게 뜬 핀 (12개 시나리오 합계) | 0 | 300개 (최대 185ms) | **0** |
| 드래그 프레임당 JS, level 3 | 2.7~2.9ms | 0.12~0.55ms | **0.14~0.76ms** |
| 드래그 프레임당 JS, level 8 | 1.2~1.3ms | 0.03~0.15ms | **0.04~0.19ms** |
| 드래그 직후 필터 반영, level 3 | 70~85ms | 235~285ms | **54~70ms** |
| 드래그 직후 필터 반영, level 8 | 21~35ms | 169~185ms | **20~34ms** |

- 시나리오: level 3·8 × 300/800/1500px/s × 가로·대각선. 보충 기준을 64px로 두면 늦은 핀이 일부 남아(최대 21ms) 80px로 정했다.
- 부착 비용을 0.1ms·1ms로 바꿔도 보완안은 변경 전과 같은 수준이었다(1ms에서 1500px/s 대각선만 같은 프레임 안 지연 2개, 변경 전 1개).
- 회귀 테스트 두 개(드래그 중 핀이 몸통이 걸치기 전에 붙는지, 놓은 직후 필터가 바로 다시 그려지는지)는 첫 구현 코드에서 실패하고 보완 코드에서 통과한다.

## 남는 제약

- 실제 저사양 Android WebView의 FPS·페인트·SDK 비용은 이번 환경에서 측정하지 않았다. 동일 데이터로 작은 이동/긴 플릭/줌 직후 이동을 기기에서 비교할 필요가 있다.
- 4ms는 협력적 예산이다. 전국 인덱스 생성, 단일 대형 군집의 구성원 조회, 한 번의 SDK 호출은 중간에 중단할 수 없다.
- 화면에 이미 붙은 많은 오버레이의 SDK 이동·그리기 비용은 남는다. 화면 자체가 매우 밀집한 경우의 별도 표시 밀도/렌더링 변경은 포함하지 않았다.

### 공사 OpenAPI 활용 실태 확인

공고문은 **"한국관광공사 OpenAPI 필수 활용"**을 참가 조건으로 못박고, 제출한 인증키로
**개발 기간 내 호출건수와 서비스 내 활용 내역을 직접 대조**한다고 명시한다.
활용 사실이 확인되지 않으면 20점을 잃는 게 아니라 **심사 대상에서 제외**된다.

**실측 결과 — 이 저장소에서 공사 API 호출을 한 건도 확인하지 못했다.**

| 검색 대상 | 결과 |
| --- | --- |
| 프런트 소스 전체 (`apis.data.go.kr`, `serviceKey`, TourAPI 식별자) | 0건 |
| `swagger.json` (509KB, 백엔드 전체 스펙)의 `contentId`·`contentTypeId`·`areaCode`·`sigunguCode` | 0건 |

유일한 정황은 백엔드 스케줄러 잡 `festivalSync`와 축제 스키마의 "**원천** 행사 장소명 / **원천** 도로명 주소" 표현이다.
외부 축제 데이터를 동기화하는 것으로 보이나, **그 출처가 공사 OpenAPI인지는 백엔드 저장소를 봐야 안다.**

**오늘 안에 확인할 것**

- [ ] 백엔드에서 `festivalSync`가 실제로 호출하는 엔드포인트가 `apis.data.go.kr/B551011/...` 인가?
- [ ] 공공데이터포털 인증키가 **팀원 누구 계정**으로 발급돼 있고, 인코딩·디코딩 키를 지금 꺼낼 수 있는가?
- [ ] 개발 기간 내 호출건수가 포털 마이페이지에 실제로 쌓여 있는가? (0이면 활용 근거가 없다)

확인 결과에 따라 데이터 활용 점수는 **최상 17점 / 현 추정 11점 / 최악 실격** 사이에서 갈린다.
**총점 69점은 "축제 데이터가 공사 API에서 온 게 맞다"를 전제로 한 값이다.**

### 02. 명소 데이터에 공사 API 2~3종 추가 연동 — `+4~6점`

**왜**: 설령 축제 데이터가 TourAPI라 해도 **활용 API가 사실상 1종**이다.
서비스의 주력인 명소(스팟)에는 붙일 자리가 많은데 비어 있어 "적절성" 배점을 크게 못 받는다.

**후보** — 스팟 상세(`/spot/[id]`)에 붙이기 좋은 순서

- 지역기반 관광정보 (`areaBasedList`) — 스팟 주변 관광지·음식점·숙박
- 상세이미지 (`detailImage`) — 스팟 기록이 없을 때의 콜드스타트 대비까지 겸함
- 반복정보 (`detailIntro`) — 이용시간·주차·문의처

**검증 기준**: 스팟 상세에서 사용자 기록 없이도 공사 데이터만으로 화면이 채워질 것.
기능설명서 4번(공사 OpenAPI 리스트)에 **3줄 이상** 적을 수 있을 것.

**주의**: 백엔드 경유가 원칙이다(`CLAUDE.md` API 호출 규칙). 프런트에서 `apis.data.go.kr`를 직접 부르면
인증키가 번들에 노출되고 CORS도 막힌다. **백엔드에 프록시 엔드포인트를 요청**해야 하므로
[BACKEND_API_REQUESTS.md](BACKEND_API_REQUESTS.md)에 항목을 먼저 올릴 것. 1~2주 비용의 대부분이 이 왕복이다.

### 03. 비로그인 둘러보기 허용 — `+3~4점`

**왜**: 지금은 **로그인 없이 아무것도 못 본다.** `src/middleware.ts`가 진입 화면(`/`, `/login`, `/onboarding`)과
가입 플로우(`/Terms`, `/profile`)를 뺀 전부를 `/login`으로 돌린다. **심사위원의 첫 화면이 곧 로그인 벽이다.**

거기에 애플·네이버 버튼이 무반응이라(05번), 카카오 계정이 없는 심사위원은 서비스를 아예 못 본다.

**할 일**: `PUBLIC_PATHS`에 읽기 전용 화면을 추가한다 — `/map`, `/explore`, `/spot/[id]`, `/festivals/[id]`, `/feed`.
찜·기록 작성 같은 쓰기 동작에서만 로그인을 요구한다.

**검증 기준**: 시크릿 창으로 서비스 URL을 열었을 때 **로그인 없이 지도에서 개화 상태가 보일 것.**

**주의**: 라우트 가드는 보안 경계가 아니라 UX 라우팅용이다(마커 쿠키 기반, 실제 인증은 백엔드가 401로 한다).
따라서 공개 전환은 안전하지만, **비로그인 상태에서 해당 API가 401을 주지 않는지** 먼저 확인해야 한다.
401이면 화면이 열려도 빈 채로 보여 오히려 역효과다.

### 04. 에러 바운더리 + 404 화면 — ✅ 완료 (2026-08-10)

**왜**: 심사 항목 "안정성" 직격. 런타임 에러 한 번이면 흰 화면이었다.

**추가한 것**

| 파일 | 역할 |
| --- | --- |
| `src/app/error.tsx` | 페이지 단위 에러. "다시 시도"(`reset`) + "지도로 가기" 이탈 경로 |
| `src/app/global-error.tsx` | 루트 레이아웃 자체가 터진 경우. 레이아웃을 대체하므로 `html`·`body`를 직접 그리고, 공용 컴포넌트에 의존하지 않는다 |
| `src/app/not-found.tsx` | 404 |

세 파일 모두 `export default`인데, 이건 규칙 위반이 아니라 **Next.js App Router가 이 파일들에 요구하는 형식**이다.
`error.digest`를 화면에 노출해 두어 문의가 들어왔을 때 서버 로그와 대조할 수 있다.

**남은 실기기 확인** (코드 레벨 검증만 끝난 상태)

- [ ] 컴포넌트에서 의도적으로 throw 했을 때 `error.tsx`가 뜨고 "다시 시도"가 동작할 것
- [ ] 없는 경로(`/zzz`)에서 `not-found.tsx`가 뜰 것
- [ ] 두 화면 모두 모바일 폭(`sm:max-w-107.5`) 안에서 정상으로 보일 것

### 05. 애플 로그인 버튼 처리 — `+1점`

**파일**: `src/app/login/_components/SocialLoginBtns.tsx`

네이버는 카카오와 같은 방식으로 연결됐다 (`src/lib/naver/naverLogin.ts`, 2026-09-01). 백엔드에

애플만 아직 핸들러가 없다. `disabled`도 아니라 정상 버튼으로 보이고,
누르면 아무 일도 일어나지 않는다. **첫 화면의 죽은 버튼**이라 완성도 인상을 즉시 깎는다.

  **프록시를 거치면 OAuth 세션 쿠키가 끊기므로 반드시 백엔드 직행이어야 한다.**

### 09. CI/CD 개선 — ✅ 완료 (2026-08-10)

### 10. 발전계획 문서화 — `+2~3점`

## 이 계획의 한계

- **추측이 섞인 부분**: 데이터 활용 11점은 "`festivalSync`가 공사 축제정보 API를 쓴다"는 가정 위의 값이다.
  아니면 이 항목은 0점이고 실격이다. 백엔드 저장소를 확인해야만 확정된다.
- **검증하지 못한 부분**: 배포된 서비스에 실제 접속해 화면·응답속도·모바일 동작을 보지 않았다.
  완성도 21점은 **코드와 문서만** 근거로 한 값이며, 실제 구동에서 문제가 더 나오면 내려간다.
  백엔드 안정성·응답속도도 범위 밖이다.
- **점수의 성격**: 심사위원 배점은 상대평가 요소가 크다. 여기 숫자는 "공고문 기준을 그대로 적용했을 때
  어디가 비어 있는가"를 보는 도구이지, 실제 득점 예측이 아니다.
